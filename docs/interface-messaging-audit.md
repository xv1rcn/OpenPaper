# OpenPaper 提示语与反馈交互审查

日期：2026-11-23。审查基线：`5115607`。以下问题清单保留审查时状态；首轮实施进度见文末，不将建议清单视为全部已完成。

## 结论

当前界面把宣传语、字段帮助、操作状态、错误、诊断信息放到了相近的视觉层级。用户要阅读论文，却先遇到大量关于应用自身的说明。主要问题不是缺少更精美的提示框，而是提示出现得过多、位置不对、含义混用、缺少结束条件。

改造目标：默认界面只显示内容与操作；用户正在作出决定、等待结果或需要处理问题时，再提供就近、简短、可操作的反馈。

## 范围和证据边界

- 源码检查：书库、侧栏、卡片、导入、筛选、分组、论文编辑、回收站、设置、外观、阅读器、PDF 控件、结构化速读、导出管理、统计与关系图；共享请求、阅读状态存储及后端生成/配置错误。
- 原生截图观察：macOS 已有论文的书库、速读设置、外观设置、已生成结果的阅读器。
- 此前本机会话直接观察：首次阅读的缓存不存在报错、PDF 导入结果、模型连接成功和失败、速读生成过程、重启恢复。
- 其余错误与确认分支通过源码确认，没有通过故意破坏用户配置、删除论文或制造权限故障来复现。
- 本轮未实际切换用户主题，未执行 Windows/Linux 界面视觉验收。深色风险来自样式检查，不能当作这些平台的实测结论。

## 三、需要修正语义和状态逻辑的反馈

这些不能只靠替换中文字符串解决。

| 编号 | 发现及证据 | 处理 |
|---|---|---|
| C01 | 首次阅读显示 `Error: 速读缓存不存在`。`loadReading` 走普通请求异常分支 | 后端给出明确的“尚未生成”状态或错误码；前端只对这个状态展示空态。其他 404、文件丢失、权限问题不能一律吞掉 |
| C02 | `ReaderWorkspace` 的顶层 error、任务 error、无 content 空态可以并存 | 建立互斥状态：加载、未生成、生成中、成功、失败。失败时不再显示“原文已就绪”的速读引导；原文面板独立可用 |
| C03 | 多处 `String(e)`、后端错误原文直接显示 | 用户层：发生了什么、是否保存成功、能做什么；技术层：可展开的脱敏详情。不要展示 `Error:`、路径、内部字段或堆栈作为主要解释 |
| C04 | `result.warning` 写入 `message`，用绿色 `settings-message` 显示 | 区分 success / warning / error。例：“配置已保存，但旧密钥未能清理”是部分成功警告，持续保留并提供处理说明 |
| C05 | 保存失败涉及旧配置是否有效 | 保留“保存失败，仍使用上次配置”这类有实际决策价值的信息；具体原因和重试操作放旁边 |
| C06 | `useLibrary.mutate` 先显示成功，再 refresh；刷新失败也可能同时出现成功和错误 | 区分写入成功与列表刷新失败：“修改已保存，列表刷新失败”；不鼓励重复提交已成功操作 |
| C07 | 保存、标记已读等成功反馈长期占据书库顶部 | 保存用就近状态或短暂通知；已读切换以卡片状态为主，读屏状态播报保留；导航离开后不遗留旧通知 |
| C08 | 外观保存后继续修改，message 不随 dirty 清空 | 编辑后立即失效旧“已保存”反馈，显示未保存状态，避免错误承诺 |

| C12 | 模型等待时展示“正在构造论文证据片段”等内部流程 | 主提示只保留“读取原文”“生成速读”“整理结果”；诊断阶段按需查看 |
| C13 | 未生成/失败/空图表仍保留全部速读章节导航 | 目录只包含可显示的内容；无图表不占空标题。关键结论缺少证据仍需保留说明，不能为简洁隐藏研究局限 |
| C14 | `StructuredRead` 用 `labels[key] || key`，暴露 `technical_explanation`、`basis`；枚举 `unknown` 等直接显示 | 使用明确的章节呈现、完整标签与枚举映射。未知字段保留在诊断/原始结果，不直接铺在正文中；重要未知内容需有兼容处理，不能静默丢弃 |
| C15 | 空字段默认都写“论文中未明确说明” | 区分模型未返回、旧缓存缺字段、原文明确未提供。缺少数据不能自动推断原文没有；非关键空字段不渲染 |
| C16 | 移入回收站也使用系统 confirm，随后再给长成功通知 | 有可靠恢复路径时使用轻量反馈“已移入回收站”+“撤销”；永久删除仍需确认 |
| C17 | 永久删除、清空配置、重新生成、放弃草稿都使用通用 confirm | 使用统一确认组件，标题说具体操作，正文只说明后果，按钮写“永久删除”“放弃修改”等具体动作；不可逆损失保留确认 |
| C18 | 重新生成会覆盖结果并调用模型 | 保留覆盖后果与费用信息；默认取消，不能为了省字直接移除确认 |
| C19 | 加密 PDF、文件损坏、连接失败等提示 | 保留，放发生问题的面板内并提供“重试”或“打开原文”；输入验证放字段旁，勿把局部问题提升为全局故障 |

## 四、视觉问题与统一规则

### 已确认的问题

1. **正常状态太醒目。** 模型设置中的绿色盾牌横幅与输入框重复表达已保存密钥，横幅还占据独立的一行和上下间距。
2. **必要信息反而过小、偏淡。** `.field-help` 为 11px，`.dialog-description` 为 12px，多处辅助说明为 10px。按源码色值计算，`#7f8c75` 对默认背景 `#fafbf8` 对比度约 3.42:1，`#839075` 对白底约 3.38:1；这不是对整个界面或自定义主题的完整对比度验收。
3. **同一种语义有多套外观。** `.notice`、`.settings-message`、`.inline-error`、`.error-banner`、`.state-save-error` 各自定义样式及生命周期；警告还混入成功样式。
4. **说明和主要操作距离过远。** 设置测试反馈在按钮上方隔着重新加载、清空配置；一次操作结果不易与触发控件关联。
5. **正文被内部结构包围。** 阅读器的目录、模型时间和嵌套字典标签抢占阅读空间；递归 `.reading-record` 造成卡片套卡片。
6. **主题覆盖不完整。** 部分错误与帮助色使用硬编码颜色，深色规则只覆盖其中一些类。应建立语义色变量并逐主题验收，而不是继续追加局部覆盖。

### 建议的反馈体系（产品决策，不是照抄外部组件规范）

| 类型 | 位置/样式 | 生命周期 | 示例 |
|---|---|---|---|
| 无需反馈的普通状态 | 由选中态、数量、内容变化表达 | 随状态变化 | 已读、视图切换、分组折叠 |
| 字段帮助 | 字段下方，12–13px，中性文字，无色块 | 仅确有解释需要时 | “0 表示自动” |
| 操作进行中 | 触发按钮 spinner + 动词，按钮宽度稳定 | 操作结束即消失 | “保存中…” |
| 普通成功 | 就近反馈或一个轻量通知，不挤动正文 | 建议 3–5 秒；进一步编辑立即清除旧保存状态 | “已保存” |
| 可撤销操作 | 一条通知 + 操作，关闭后仍能从回收站恢复 | 建议 8 秒，悬停/键盘聚焦暂停计时 | “已移入回收站 · 撤销” |
| 局部错误 | 相关字段/面板附近，图标 + 文字 + 恢复操作 | 直到修复或用户明确处理 | “连接失败 · 重试 · 详情” |
| 部分成功警告 | 中性/警告色、说明未完成部分 | 不自动隐藏 | “配置已保存，旧密钥未能清理” |
| 全局服务或保存故障 | 紧凑持久横幅，不遮挡操作 | 恢复后撤除 | “阅读位置未保存 · 重试” |
| 破坏性确认 | 统一应用内对话框 | 必须作出选择 | “永久删除这篇论文？” |
| 技术诊断 | 默认折叠、可复制、脱敏 | 用户主动查看 | 状态码、阶段、模型用量 |

视觉基线：正文 14px，辅助文本 12–13px；行高约 1.5；图标 14–16px；只用淡色背景强调实际错误/警告，普通成功不再使用整页宽绿色块。尺寸按 CSS 像素，不按 Retina 截图像素。颜色通过语义变量提供浅色、暖纸、深色版本，并实测对比度。

同一操作只设一个主要反馈位置。全局同时最多一条普通通知；重要错误不能被后来的“已复制”覆盖。提示不要抢焦点。错误不能仅依赖颜色区分。

## 五、保留的无障碍与必要信息

- `SettingsPanel` 的“应用外观与速读配置。”已有 `sr-only`，不属于屏幕上的视觉冗余；可缩短但保留对话框描述关联。
- `aria-label`、图标按钮名称、输入标签、状态播报不能随可见文字一起清除。
- 正常状态使用 `role=status` 等非打断播报；真正需要立即注意的错误才使用 `role=alert`。生成进度不应每 1.5 秒重复朗读无变化内容。
- 不把关键费用、删除后果、保存失败、导出范围、统计口径和研究证据不足全部藏进 tooltip。
- 自动消失通知不是唯一恢复入口；键盘、读屏和低速阅读用户都应能找到后续动作。
- 密钥存储诊断可保留安全错误码，但不展示密钥、凭据原值或原始异常中的敏感信息。

## 六、实施顺序与验收

### 第一批：减少默认界面噪音

处理 A01–A14；合并数量与标题；字段状态就近呈现；统一“书库/速读/保存”等术语。清理对应 CSS，避免删文案后留下同样大的空白。此阶段不改变数据和凭据逻辑。

### 第二批：建立统一反馈和错误状态

新增共享 Feedback/Toast/ConfirmDialog，明确 severity、scope、action、details 和关闭策略；设置拆分 warning 与 success；共享请求增加可识别错误码，后端提供业务状态。优先修复未生成报错、过期“已保存”、成功与失败同时显示、技术异常直出。

### 第三批：阅读与配置交互收口

阅读空态与任务状态互斥；目录按内容生成；结构化内容定制渲染，避免空字段和英文键；技术信息折叠；简要模式的输出长度在生成约束和呈现两个环节处理，不靠截断重要内容实现。

### 验收清单

- 空库、已有论文、筛选无结果、空回收站各自只有一个清晰空态/标题，不显示重复口号。
- 首次阅读不出现缓存不存在错误；真实文件丢失/权限失败仍可见且可处理。
- 保存成功后再次编辑，不再显示“已保存”；连接测试失败不覆盖保存状态的含义。
- 旧凭据清理失败不会显示为完全成功；旧配置仍有效等重要后果不会被删除。
- 一次操作只有一个主要反馈；修改成功但刷新失败准确表达部分成功。
- 生成中只有必要的阶段提示；失败时不同时显示未生成引导；无内容章节不占位。
- 不显示内部英文键或枚举；未知字段有兼容路径；真实证据缺失不会为追求简洁被隐藏。
- 导入全成功、部分失败、重复、超限分别可辨认；失败条目不会自动消失。
- 撤销、永久删除、放弃草稿、重新生成各自使用符合后果的交互。
- 浅色、暖纸、深色；默认 1024×768；窄窗口；长中文错误；键盘与读屏全部复查。
- Windows/Linux 单独验证原生对话框、快捷键和提示不被遮挡；本机 macOS 通过不能代替。

## 参考依据

这些资料用于校验原则；具体删除项、位置、尺寸、时长及实施顺序来自本项目审查。

- [NN/g：Error-Message Guidelines](https://www.nngroup.com/articles/error-message-guidelines/)：错误要靠近问题源，用用户可理解的语言说明问题和恢复方法，强度匹配后果。
- [W3C：Understanding SC 4.1.3 Status Messages](https://www.w3.org/WAI/WCAG21/Understanding/status-messages)：状态变化应能被辅助技术识别，不必抢焦点；精简视觉不等于移除语义。
- [Material：Snackbars](https://m3.material.io/components/snackbar/overview)：短暂过程反馈与内容区分离的组件参考；不将 snackbar 用作持久错误的唯一承载方式。
